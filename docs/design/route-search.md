# 経路探索エンジン 設計書

- 状態: ドラフト（2026-10-08）
- 対象: `backend/assets`（列車時刻表の軽量化）、`backend/internal/route`、`GET /api/journeys`
- 関連: [AI 鉄道エージェント 設計書](ai-api.md)

---

## 1. 目的

出発駅・到着駅・時刻の条件から、都営交通の路線内の経路を求める。

このエンジンは AI を使わない。AI エージェント（[ai-api.md](ai-api.md)）は、このエンジンを道具（`search_route`）として呼び出し、結果を比べて説明するだけにする。経路の正しさは、すべてこのエンジンが決める。

AI が使えないとき（上限到達・障害）でも、API（と、作る場合は経路検索の画面）からこのエンジンを直接使える。

---

## 2. 対応範囲

- 対象は都営交通の6路線（浅草線・三田線・新宿線・大江戸線・荒川線・日暮里・舎人ライナー）。
- 直通運転で他社線に乗り入れる列車も、都営線内の区間だけを扱う。
- 都営以外の駅を出発・到着に指定された場合は、対象外として扱う。
- 作りは事業者に依存させない（10章）。ID は `odpt.Station:<事業者>.<路線>.<駅>` のまま扱い、都営に決め打ちした処理を入れない。

## 3. データ

### 3.1 使うデータ

| データ | 取得元 | 用途 |
|---|---|---|
| 列車時刻表 | `https://api-public.odpt.org/api/v4/odpt:TrainTimetable.json`（全件ダウンロード用。APIキー不要） | 経路探索の本体 |
| 駅 | 既存の `assets/station.json` | 駅名・乗り換え駅の判定 |
| 遅延 | 既存の `odpt:Train`（リアルタイム） | 7章 |
| 運行情報 | 既存の `odpt:TrainInformation`（リアルタイム） | 7章 |

列車時刻表の全件版（2026-10-08 に取得して確認）の内容は次のとおり。

- 列車 5,600 本、停車 12.2 万件。路線ごとの本数は、浅草線 1,260、荒川線 1,060、日暮里・舎人ライナー 928、大江戸線 839、三田線 758、新宿線 755
- 全列車に、終点に着く時刻が入っている
- 停車ごとに、駅と到着時刻・発車時刻を持つ。始発駅は発車時刻だけ、終点は到着時刻だけ
- 時刻は `HH:MM`（00:00〜23:59）。0時台が 1,318 件ある
- 行先が2駅以上ある列車はない
- ダイヤ種別は4種類（平日・土休日・土曜・休日）

### 3.2 使わないデータ

| データ | 使わない理由 |
|---|---|
| 公開 API の列車時刻表（`odpt:TrainTimetable?odpt:operator=...`） | 1回の取得が 1,000 件までで、途中で切れる。今の `assets/train_timetable.json` はこの状態 |
| 駅時刻表 | 駅ごとのデータなので、列車ごとにつなぎ直す必要がある。到着時刻もなく、終点に着く時刻が分からない |
| GTFS（`Toei-Train-GTFS.zip`） | 内容は列車時刻表と同等で、zip にしたときの大きさもほぼ同じ（JSON 0.79MB、GTFS 0.74MB）。ただし列車種別がなく、ID の形式が既存の画面と違う。時刻表のデータ源が2つになる。他の事業者を GTFS でしか取れない場合に改めて検討する |
| GTFS-Pathways | 大江戸線の12駅の、出入口からホームまでの通路だけ。別の路線への乗り換え通路は入っていない。コンテスト期間だけの公開でもある |
| GTFS-RT（TripUpdate・Alert） | 遅延は路線・方向ごとに扱うので（7章）、列車ごとの遅延は不要。既存の JSON で足りる |

### 3.3 軽量な形式への変換

列車時刻表の全件版は 25.5MB ある。そのまま埋め込むと、起動のたびに JSON を解析することになり、コールドスタートが遅くなる（駅時刻表を軽量化する前の Init Duration は 760〜1,150ms だった）。そこで、駅時刻表（`assets/slim`）と同じく、使う項目だけに絞った形式に変換して埋め込む。

```
scripts/update_assets.sh
  └ 全件版を取得 → assets/train_timetable.json（25.5MB）
go generate ./assets
  └ cmd/gen-assets が assets/train_timetable.gob を生成
go:embed
  └ train_timetable.gob だけを埋め込む（json は埋め込まない）
```

```go
// assets/slim
type TrainTimetables struct {
    Strings []string // 列車ID・列車番号・路線・ダイヤ種別・方面・列車種別・駅ID。0 番は空文字
    Trains  []Train
}

type Train struct {
    Train, TrainNumber, Railway, Calendar, RailDirection, TrainType, Destination int32 // Strings の番号
    Stops []Stop
}

type Stop struct {
    Station   int32 // Strings の番号
    Arrival   int16 // 運行日の0時からの分。無い場合は -1
    Departure int16 // 同上
}
```

- 時刻は、起動時に毎回文字列から変換しないよう、生成するときに分の整数にしておく。3時前の時刻は翌日として扱い、24時間を足す（`00:15` → `24:15` = 1455）。運行日を3時で区切る扱いは `internal/calendar` と同じ。
- 捨てる項目: `@id`、`@context`、`dc:date`、`dct:issued`、`owl:sameAs`、番線、`odpt:isOrigin` など。
- 駅時刻表と違い、読み込んだあとに `model.TrainTimetable` には戻さない。数値のまま経路探索エンジンに渡す。12 万件の停車ごとに文字列を作らずに済む。

大きさの見込み（試作で計測）は次のとおり。

| | そのまま | zip 圧縮後 |
|---|---|---|
| 全件版の JSON | 25.5MB | 0.79MB |
| 軽量な形式 | 1.26MB | 0.37MB |

今の `train_timetable.json`（5.1MB、1,000 件で途切れていて、どこからも使われていないのに起動のたびに解析している）と入れ替わるので、実行ファイルは今より約 4MB 小さくなる。

JSON は、今の駅時刻表と同じくリポジトリにも置く。Git は内部で圧縮して保存するので、ダイヤ改正1回あたりの増え方は 1MB 弱の見込み。他の事業者を足すときに、置き方を見直す（10章）。

### 3.4 データの更新

- 時刻表は、ダイヤ改正のとき（年に1〜2回）に手動で取り直し、再デプロイする。今の `assets` と同じ運用。
- 遅延と運行情報は、リクエストのたびにアプリが自動で取得する（7章）。

## 4. 乗り換え

- 同じ名前の駅（新宿・大門・春日・三田・神保町・蔵前・森下・熊野前の8駅）を、乗り換えられる駅として扱う。名前が違うが乗り換えられる駅（東日本橋 ⇔ 馬喰横山）は、個別に対応表に足す。
- 乗り換えにかかる時間（歩く時間＋余裕）は、データにないので一律にする。
  - 別の路線の駅への乗り換え: 5分（`service/transfer.go` の `transferMinutes`）
  - 同じ駅で同じ路線の別の列車に乗り継ぐ場合（例: 各停から快特へ）: 1分（`route.Config.SameStationMinutes`）。同じホームか向かいのホームで乗り継げるので、短くする。乗り換え回数には数える。
- 実データの代表的な経路で確認した結果、5分で始める。春日（三田線 → 大江戸線）は乗り換えに6分、蔵前（大江戸線 → 浅草線。改札の外を歩く）は8分の余裕がある経路が選ばれた。蔵前のように通路の長い駅で足りなければ、駅ごとの時間を対応表に持たせる（エンジンは変えずに済む）。
- 乗り換えの対応表は、エンジンとは別のデータとして持つ（`route.Transfer` の一覧を service が作って渡す）。事業者を足したときに、表を差し替えたり足したりできるようにする。
- 出発駅・到着駅に同じ名前の駅を指定した場合は、路線が違っても1つの駅としてまとめて扱う。三田線の春日を指定しても、乗り換え時間なしで大江戸線の春日から乗る経路を返す（乗る前に歩く時間は、乗り換えとして数えない）。

## 5. 経路探索の方式

### 5.1 RAPTOR を使う

RAPTOR は、乗り換え回数を1回ずつ増やしながら、各駅に最も早く着ける時刻を求める方式。乗り換え 0 回・1 回・2 回…ごとに最も早い経路が出るので、次の用途に合う。

- 「乗り換えは少なめで」という希望に応える
- AI エージェントが、乗り換え回数と到着時刻の違う候補を比べて推薦する

### 5.2 索引

ダイヤ種別の組み合わせごとに、初めて探すときに作ってメモリに置く（8章）。到着時刻の指定（5.3）のために、時刻を反転させた逆向きの路線網も作る。

- **路線パターン**: 停車駅の並びが同じ列車をまとめる。各パターンの中で列車を発車時刻順に並べる。
- **駅 → パターン**: その駅を通るパターンの一覧。
- **乗り換え**: 駅 → 乗り換えられる駅と、かかる時間。

注意する点は次のとおり。

- 大江戸線の環状部では、1本の列車が同じ駅（都庁前）を2回通る。駅の並びに同じ駅が2回出てきてもよい作りにする。
- 快特などの停車駅の違う列車は、別のパターンになる。
- 列車IDは平日と土休日で使い回されるので、列車はダイヤ種別と列車IDの組で区別する。

### 5.3 時刻の指定

| 指定 | 動き |
|---|---|
| `departAt`（出発時刻） | その時刻以降に出発して、最も早く着く経路を求める |
| `arriveBy`（到着時刻） | その時刻までに着く経路のうち、最も遅く出発するものを求める（時刻表を逆向きにたどる） |
| どちらもない | 現在時刻（JST）に出発するものとして扱う |

- その日に使うダイヤ種別は `internal/calendar` で決める（3時前は前日の運行日として扱う）。
- 指定した時刻は、現在の運行日の時刻として扱う。3時前の時刻はその運行日の深夜（`00:30` → 24:30）になる。日付の指定は今はできない。
- 終電を過ぎて経路がない場合は、経路なしとして返す。翌日の始発までは探さない（初期）。

### 5.4 結果の数

- 乗り換え回数ごとに、最も早く着く経路を1本ずつ返す。乗り換え回数の上限は3回（初期値）。
- 乗り換えが多いのに、少ない経路より早く着かない経路は返さない。
- `departAt` で見つけた経路は、同じ時刻に着く経路のうち最も遅く出るものに絞る（到着時刻からさかのぼってもう一度探す）。最初の列車に早く乗りすぎて、乗り換え駅で長く待つ経路を避けるため。`arriveBy` も同じように、同じ時刻に出る経路のうち最も早く着くものに絞る。

## 6. API

```
GET /api/journeys?from=<駅ID>&to=<駅ID>&departAt=<HH:MM>|arriveBy=<HH:MM>&maxTransfers=<n>&avoid=<路線ID,...>&realtime=<true|false>
```

- `realtime=false` を指定すると、遅延と運転見合わせ（7章）を反映せず、時刻表どおりに探す（`delayApplied` は `false`）。省略時は反映する。

- `/api/routes` は路線一覧で使っているので、別の名前にする。
- `avoid` で指定した路線は使わない（7章の運転見合わせや、AI が探し直すときに使う）。
- 駅名からの検索はしない。駅名から駅IDへの変換は、AI の道具（`find_station`）と画面の駅選択で行う。

レスポンスの例:

```json
{
  "journeys": [
    {
      "departureTime": "10:02",
      "arrivalTime": "10:31",
      "transfers": 1,
      "legs": [
        {
          "railway": "odpt.Railway:Toei.Mita",
          "train": "odpt.Train:Toei.Mita.1035T",
          "trainType": "odpt.TrainType:Toei.Local",
          "destination": "odpt.Station:Toei.Mita.Mita",
          "from": "odpt.Station:Toei.Mita.Kasuga",
          "to": "odpt.Station:Toei.Mita.Mita",
          "departureTime": "10:02",
          "arrivalTime": "10:12",
          "delayMinutes": 0
        }
      ]
    }
  ],
  "delayApplied": true,
  "suspendedRailways": []
}
```

- 駅名・路線名・種別名・行先名は、ID と別の項目（`fromName`・`railwayName`・`trainTypeName`・`destinationName` など）で日本語のラベルも返す。
- `delayApplied`・`suspendedRailways`・`delayMinutes` は7章（PR 3）で足した。`departureTime`・`arrivalTime` は遅れを足した時刻で、時刻表の発車時刻は `departureTime` から `delayMinutes` を引いた時刻になる。
- エラー: 必須パラメータの不足・時刻の形式・`departAt` と `arriveBy` の両方の指定・`maxTransfers` の範囲（0〜3）・存在しない路線の `avoid`・同じ駅の指定は 400、存在しない駅は 404。経路が無い場合は 200 で `journeys` を空にする。
- DTO を変えたら、Swagger・フロントの `src/types.ts`・`src/api.ts` も合わせて変える。

## 7. 遅延と運転見合わせ

列車ごとではなく、**路線・方向ごと**に扱う。路線が遅れているときは、その路線のほとんどの列車が遅れるので、推薦の判断（遅れている路線を避けるか）にはこれで足りる。列車ごとに扱わないので、遅延データの列車と時刻表の列車を対応づける必要もない。

| 判断すること | 使うデータ | 方法 |
|---|---|---|
| 何分くらい遅れているか | `odpt:Train` の `odpt:delay`（秒） | 路線・方向ごとの中央値を求め、その路線・方向のこれから出る列車すべてに足して探す |
| 運転を見合わせているか | `odpt:TrainInformation` の文章 | 「見合わせ」「運休」などの言葉で判定し、その路線を `avoid` に入れて探す |
| 日暮里・舎人ライナー・荒川線 | `odpt:TrainInformation` の文章だけ | 日暮里・舎人ライナーは `odpt:Train` が配信されず、荒川線は `odpt:delay` が null で配信されるので、遅延の分数は反映できない |

- 運行情報の文章は、平常時は「現在、15分以上の遅延はありません。」のようになっていて、状態を表す項目はない。15分未満の遅れは文章からは分からないので、分数は `odpt:Train` から求める。
- 判定の結果は、路線ごとに「平常 / 遅延（◯分）/ 見合わせ」の3つにまとめる。AI の道具（`get_train_status`）にも、この形で渡す（AI エージェントの PR で作る。経路探索で使うのは遅れの分数と見合わせだけ）。
- 遅延は現時点の値なので、反映するのは近い時間帯だけにする。現在から1時間後（`DelayUntil`）までの時刻に遅れを足し、それより後の時刻は「`DelayUntil` + 遅れ」より前にならないように後ろへずらす。時刻の前後が入れ替わらない変換なので、パターン（追い越しの無い列車の並び）と二分探索はそのまま使える。パターンは路線・方向ごとに分ける。
- 見合わせは「見合わせ」「運転を中止」「運転中止」を含み、「再開」を含まない文章で判定する（`service/realtime.go`）。過去の文章は集められなかったので、見合わせの文章が出たら確かめて言葉を足す。一部区間の見合わせでも路線全体を `avoid` に入れ、レスポンスの `suspendedRailways` で知らせる。検索する時刻にかかわらず避ける。
- 遅れの分数は、路線・方向ごとの `odpt:delay` の中央値（件数が偶数なら後ろの値）を分に丸めたもの。
- 遅延と運行情報の取得結果は30秒キャッシュする。取得は3秒で打ち切る。
- 取得に失敗した場合は、遅延も見合わせも反映せずに時刻表どおりに探し、レスポンスの `delayApplied` を `false` にする。

## 10. 他の事業者への拡張（将来）

- 東京メトロ・JR東日本・私鉄などは、APIキー（ODPT の開発者登録）が必要になる。JR東日本・京急・西武・京王・東武・東急は「チャレンジ2026限定」のデータで、使える期間や公開の条件を確認してから使う（チャレンジの開催期間は 2026-07-01〜2027-03-12）。
- 事業者をまたぐ乗り換え（JR新宿 ⇔ 都営新宿 など）の対応表が必要になる。
- データの量が数十MB 程度になる見込み。そのときに次を検討する。
  - 読み込みに変換がいらない形式（数値の配列をそのままバイト列にする）
  - 経路探索を別の Lambda に分ける
  - 時刻表を定期的に自動で取得し、S3 に置く（EventBridge Scheduler）。リポジトリに JSON を置かない
- GTFS しか取れない事業者がある場合は、GTFS の読み込みを追加する。
