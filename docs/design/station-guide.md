# 駅の中の案内（何両目に乗るか・どこへ歩くか） 設計書

- 状態: ドラフト（2026-10-28）
- 対象: `scripts/update_assets.sh`・`cmd/gen-assets`（案内の表の生成）、`backend/assets`（読み込み）、`internal/service`（経路検索の結果に付ける）、フロントの経路の表示
- 関連: [経路探索エンジン 設計書](route-search.md)、[対象を東京都内の鉄道に広げる 設計書](multi-operator.md)

---

## 1. 目的

経路検索の結果で、乗り換える駅や降りる駅について、次のことを案内する。

- 乗る列車の**前から何両目**に乗ると、降りたあと近いか
- 降りてから**どの階段・エスカレーター・エレベーター**を使い、**どのホーム・改札**へ、何 m・何分歩くか

例: 「新宿で降りたら → 前から3両目付近の階段 → 山手線（渋谷・品川方面）のホーム 約120m・2分」

最初は、いちばん迷いやすい JR 新宿駅で作り、同じ仕組みで JR の残りの5駅に広げる。

---

## 2. 対応範囲

| 項目 | 範囲 |
|---|---|
| 駅 | JR東日本の6駅（新宿・東京・池袋・渋谷・品川・高輪ゲートウェイ）。データがこの6駅にしか無い（3章）。まず新宿 |
| ホーム | 各駅の JR の在来線のホーム。新幹線のホームは経路検索の対象外なので扱わない |
| 案内する場面 | (1) 同じ駅で JR から JR へ乗り換えるとき: 乗り換え先のホームまで。(2) JR から他社へ乗り換えるとき: 他社の乗換口に近い JR の改札まで（6.3）。(3) 経路の最後に JR で降りるとき: 案内しない（行き先の出口が分からないので。12章） |
| 他社の駅の中 | データが無いので扱わない（新宿なら小田急・京王・メトロ・都営のホームと通路） |

## 3. データ

### 3.1 取得元

ODPT のデータセット「歩行空間ネットワークデータ（JR東日本 ○○駅）」（提供: JR東日本コンサルタンツ、**公共交通オープンデータチャレンジ限定ライセンス**）。1駅につき ZIP が2つあり、チャレンジ用のキー（`ODPT_CHALLENGE_CONSUMER_KEY`）で、次の URL から取れる（2026-10-28 に6駅とも取得を確認。Azure の一時的な署名付き URL へリダイレクトされる）。

```
https://api-challenge.odpt.org/api/v4/files/JR-East/data/jrc_nwd_<駅>_geojson.zip         歩行空間ネットワーク
https://api-challenge.odpt.org/api/v4/files/JR-East/data/jrc_stationmap_<駅>_geojson.zip  構内地図
<駅> = shinjuku / tokyo / ikebukuro / shibuya / shinagawa / takanawa_gateway
```

- 同じ形式の、国土交通省が整備した大江戸線12駅のデータ（公共データ利用規約）もあったが、チャレンジ2025の終了で公開が終わっている（2026-10-28 に確認）
- ODPT の駅施設データ（`odpt:StationFacility`。号車ごとの階段・乗換の案内を入れる型）は、どの事業者・どのホストでも 404 で、提供されていない

### 3.2 中身

**歩行空間ネットワーク**（国交省「歩行空間ネットワークデータ整備仕様」2024年7月）

- 点（`node.geojson`）: 緯度・経度・階（`floor`。-5〜2、1.5 のような中間の階もある）
- 線（`link.geojson`）: 両端の点・長さ（m）・経路の種類（`route_type`）。種類は、長さと階の変わり方から次のように読める: 1 平らな通路、4 エレベーター、5 エスカレーター、6 階段、7 スロープ
- 幅・段差・手すりなどの属性は、ほぼすべて「不明（99）」
- 駅の中が1つにつながっている（東京駅で確認）

**構内地図**（国土地理院「階層別屋内地理空間情報データ仕様書」2019年3月）。階ごとのファイル

- `Space`（区画）: ホームはカテゴリ `B028` の細長い区画
- `Facility`（設備）: `F011` 階段、`F012` エレベーター、`F013` エスカレーター、`F014` スロープ、ほかにトイレなど
- `Opening`（開口部）・`Fixture`（造作）・`Floor`（階）

### 3.3 新宿駅で確かめたこと（2026-10-28）

- ホームの区画が8つ（JR の1〜16番線の島式ホームの数と合う）。長さは 267〜337m
- ホームの上の階段・エスカレーター・エレベーターの位置が、ホームの端から何 m かで出せる（例: 西端のホーム 57m 階段・59m エスカレーター・79m エレベーター・93m 階段…）
- 1つのホームの上に、ネットワークの点が34〜82個ある
- **名前が1つも無い**。区画・開口部のどれがどの改札かは書かれていない（東京駅には改札名がある）
- 改札機と見られる造作（`C202`）の固まりが13か所ある（2F に6、B1 に5、B2 に2）。カテゴリの番号は駅によって違う（東京駅は `C104`）

### 3.4 データに無いもの

| 無いもの | 補い方 |
|---|---|
| ホームがどの路線・方向か | 手で対応表を作る（5章） |
| 改札の名前 | 手で対応表を作る（5章） |
| 編成の両数 | 手で路線ごとに決める（5章）。ODPT の JR の列車時刻表にも両数・番線は入っていない（2026-10-09 取得のデータで確認） |
| 列車がホームのどこに止まるか | 進む方向の端にそろえて止まるとする（7章） |
| 号車の番号の向き | 号車ではなく「前から何両目」で案内する（7章） |

## 4. データの置き場所とライセンス

チャレンジ限定ライセンスなので、ほかのチャレンジのデータと同じに扱う（[multi-operator.md](multi-operator.md) 4章・10.2）。

- 取得した ZIP は、ほかの元データと同じく `backend/.odpt-cache/`（gitignore 済み）に置く
- 生成した案内の表（`assets/extra/station_guide.json`）はコミットせず、`assets/extra` の版に入れて非公開の S3 に置く
- 手で作る対応表（5章）は、区画の ID と自分で付けた名前だけで、データの全部や大部分を復元できるものではないのでコミットする（`tokyo_stations.txt` と同じ考え方）
- `station_guide.json` は、今の `extraFiles`（すべてそろっているか、すべて無いか）に入れず、無くても動く別のファイルにする。今の S3 の版を作り直さなくても、ほかの機能が止まらないようにするため
- ライセンスの画面に、出典（JR東日本コンサルタンツ「歩行空間ネットワークデータ」）を足す
- 2027年3月12日より前に、ほかのチャレンジのデータと一緒に消す（multi-operator.md 10.2 の手順に、このデータと手で作った対応表を足す）

## 5. 手で作る対応表

`backend/assets/guide/<駅>.yaml`（コミットする）。駅ごとに1ファイル。

```yaml
station: odpt.Station:JR-East.Yamanote.Shinjuku   # 経路検索の駅ID（同じ名前の JR の駅はすべてこの案内を使う）
platforms:                                         # ホームの区画（Space B028）の ID → 番線と路線・方向
  - space: 1a2b...
    sides:
      - track: "14"
        railway: odpt.Railway:JR-East.Yamanote
        direction: odpt.RailDirection:InnerLoop
      - track: "15"
        ...
gates:                                             # 改札機の固まりの代表点 → 改札の名前
  - name: 南口
    floor: 2F
    lat: 35.68942
    lon: 139.70024
transfers:                                         # 乗り換え先の事業者 → 使う改札（6.3）
  odpt.Operator:Odakyu: 西口
cars:                                              # 路線ごとの編成の両数（決まらない路線は書かない）
  odpt.Railway:JR-East.Yamanote: 11
```

- 番線・路線と改札の名前は、JR東日本の駅の構内図（公式サイト）と照らして決め、PR でユーザーに確かめてもらう。地図の上で区画と改札の位置を描いた画像を、確認用に生成する（`gen-assets` の確認用の出力。コミットしない）
- 島式ホームの1つの区画に、両側の番線（2つの路線・方向）が載る。7章の計算は区画の軸だけを使うので、どちらの側かは区別しない
- 両数は路線ごとの代表の値を書く。湘南新宿ラインの10両と15両のように混ざる路線は、長いほうにする（ホームの端から数えるので、前のほうの案内は両数によらない）

## 6. 案内の表の生成

`cmd/gen-assets -kind guide`（`scripts/update_assets.sh` から実行）。ZIP と対応表から、駅ごとに次の表を作る。実行時にネットワークの計算をしないよう、結果だけを持つ。

### 6.1 ネットワーク

- 点と線を読み、線の長さを重みにした無向グラフを作る（エスカレーターの向きは不明なので両方向とする）
- 階段・エスカレーターは、1階上り下りするごとに15秒（20m 相当）を足す。歩く速さは 80m/分（[multi-operator.md](multi-operator.md) 6.2 と同じ）
- エレベーターは待ち時間があるので1回60秒を足す。エレベーターだけの経路（ベビーカー・車いす向け）は、最初は作らない（12章）

### 6.2 ホームの位置

- ホームの区画の頂点から主軸を求め、軸に沿った位置（0m〜長さ）で、ホームの上の点（区画の中にあるネットワークの点）の位置を表す
- 区画の両端のうち、方向ごとに「次の駅に近い端」を前の端とする（次の駅は路線の駅の並びと座標から決める。手で決めない）

### 6.3 行き先

| 行き先 | ネットワークの点 |
|---|---|
| JR の別のホーム（番線） | その区画の中の点すべて |
| 改札 | 対応表の改札の代表点に最も近い、同じ階の点 |

他社への乗り換えは、対応表の `transfers` の改札を行き先にする。

### 6.4 出力

```
(駅, 降りるホームの路線・方向, 行き先) → {
  前から何両目, 両数,
  ホームを出る設備（階段・エスカレーター・エレベーター）,
  歩く距離（m）, 歩く時間（分、切り上げ）
}
```

- 行き先ごとに、ホームの上の各点からの最短距離を求める（行き先から1回 Dijkstra）
- 1両20m とし、前から k 両目の車両の中央の位置 `c_k` について、`min_u (|c_k − 位置(u)| + 距離(u))` が最小の k を選ぶ（u はホームの上の点）
- 両数が対応表に無い路線は、両数を出さず、ホームの前の端から何 m の階段かだけを持つ（画面では「前から何両目」を出さない）

---

## 7. 何両目の求め方の仮定

- 列車は、進む方向のホームの端にそろえて止まるとする。実際の停止位置はホームの端から数 m〜十数 m ずれるので、案内は「前から3両目**付近**」とし、1両ずれうるものとする
- 号車の番号は路線によって前から数えるか後ろから数えるかが違い、データに無いので、出さない。「前から何両目」は進行方向で決まるので、向きの取り違えが起きない
- 両数が路線の中で変わる場合（10両と15両）は、ホームの前の端から数えるので、前のほうの車両の案内は変わらない。後ろのほうを案内するときは、短い編成では無い車両を案内しうる。最初は対応表の両数のまま出し、目立つずれがあれば路線ごとに見直す

## 8. API

経路の区間（`JourneyLeg`）に、降りる駅の案内を足す。案内の無い区間では項目を返さない。

```json
{
  "railway": "odpt.Railway:JR-East.ChuoRapid",
  "to": "odpt.Station:JR-East.ChuoRapid.Shinjuku",
  "alightGuide": {
    "carFromFront": 3,
    "cars": 10,
    "via": "stairs",
    "target": "山手線 14番線",
    "walkMeters": 120,
    "walkMinutes": 2
  }
}
```

- `via`: `stairs` / `escalator` / `elevator` / `slope`
- `target`: 乗り換え先のホーム（「山手線 14番線」）か改札（「西口改札」）
- `carFromFront`・`cars` は、両数が決まらない路線では返さない
- service は、区間 i の降りる駅が案内のある駅で、次の区間 i+1 が同じ駅の JR の別のホームから出るなら、そのホームを行き先にする。i+1 が他社なら `transfers` の改札を行き先にする。直通運転で乗り続ける区間（`through`）と、同じホームで乗り継ぐ場合は案内しない
- DTO を変えるので、Swagger・`src/types.ts`・`src/api.ts`・`e2e/data.ts` を合わせる
- 経路検索の乗り換え時間（今は直線距離の式。[multi-operator.md](multi-operator.md) 6.2）には、最初は使わない（12章）

## 10. テスト

## 13. 段階2の実装（2026-10-28）

### 13.1 対応表の作り方（新宿）

5章の形から、次のように変えた。

- **階はホーム・改札ごとに書く**（`floor`）。構内地図の階の番号（`Floor` の `ordinal`）は、歩行空間ネットワークの階と合っていない（新宿の構内地図は 1F が 0、ネットワークは 1）。書くのはネットワークの階
- **改札は名前と座標で書く**。構内地図の開口部に名前が無いので、改札機と見られる造作の固まりの中心を拾った。生成のときは、同じ階で最も近いネットワークの点（30m 以内。新宿はどれも 5m 以内）を改札とする
- 番線と路線・方向は、Wikipedia「新宿駅」ののりばの表（JR東日本の駅構内図が出典）による。JR東日本のサイトは機械からの取得を拒む（403）
- 区画と番線の対応・改札の名前は、OpenStreetMap のホームの番線（`ref`）と改札の位置で照らした（照らすのに使っただけで、OSM のデータは置かない）。新宿は番線が東から西へ大きくなる。13〜16番線は OSM に番線が無く、並びから決めた
- 5・6番線（特急）・9・10番線（中央本線の特急）は、経路検索に特急が無いので書かない
- 乗り換え先の他社の駅は、小田急 → 小田急線乗換改札、京王線 → 中央西改札、京王新線・都営新宿線 → 南改札（Wikipedia の京王の新宿駅の説明による）。書いていない駅（大江戸線・丸ノ内線）は、段階3で駅の座標に最も近い改札にする
- 両数: 山手線 11、中央線快速 12、中央・総武線各駅停車 10、埼京線 10、湘南新宿ライン 15

### 13.2 データの癖

- 新宿のネットワークに、点の無い線が 1,062本中2本ある。捨てる（ログに出す）
- 山手線の路線データの駅の並びは、大崎で始まり大崎で終わる。最初と最後が同じ駅の路線を環状として、端で反対の端につなぐ
- 終点では次の駅が無いので、前の駅の反対の端を前の端とする（段階4の東京駅の中央線快速など）

### 13.3 結果（新宿、182件）

確認用の画像（`-preview` で書く SVG）で、ホームの区画・前の端・改札の位置が地図と合うことを確かめた。代表的な結果:

| 中央線快速 上り（7・8番線） | 山手線 内回り 14番線 | 5/12両目 | エスカレーター | 81m・2分 |
| 中央線快速 上り | 東改札 | 12/12両目 | エスカレーター | 65m・2分 |
| 中央線快速 上り | 甲州街道改札 | 1/12両目 | エスカレーター | 51m・1分 |

| 埼京線 南行（1・2番線） | 山手線 外回り 15番線 | 9/10両目 | エスカレーター | 147m・3分 |

### 13.4 本番に入れるとき（段階3）

`station_guide.json` は `extraFiles`（Makefile の `EXTRA_FILES`）に入れていない。段階3で、`EXTRA_FILES` に足して `make backend-extra-upload` で版を作り直す。そのときまでは、手元で `update_assets.sh` を実行すると、手元のビルドにだけ入る。
