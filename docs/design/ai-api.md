## 1. 目的

現在地と目的地を伝えると、遅延や運転見合わせを確認したうえで経路を推薦する AI エージェントを提供する。

想定する入力の例は次のとおり。

- 「今春日にいる。浅草に行きたい」
- 「新宿から浅草まで、18時までに着きたい。乗り換え少なめで」
- 「この駅から次に出る電車は？」「今遅れている路線はある？」（補助的な照会）

AI の役割は、ユーザーの意図を理解すること、必要な情報を集める手順を自分で決めること、結果を比べて自然な文章で説明することに限る。駅・時刻・経路・運行状況といった事実は、すべてアプリケーション側の正確なデータとロジックから取得する。

### エージェントと呼ぶ理由

1回の質問に対して、AI が次の手順を自分で判断して進める。

1. 駅名から駅を特定する。候補が複数あれば聞き返す
2. 運行状況を確認する
3. 経路を探す
4. 結果を見て、見合わせ中や大きく遅れている路線を含む経路なら、その路線を外して探し直す
5. 候補を比べ、理由を付けて推薦する（例: 「三田線が10分遅れているので、大江戸線経由の方が早く着きます」）

どの道具を、どの順に、何回呼ぶかは AI が決める。アプリは道具を正確に実行し、回数と時間の上限を守らせる。

---

## 2. 基本方針

1. **AI に事実を決めさせない。** 駅・時刻表・経路・運行情報・列車位置は、アプリケーションが持つデータとロジックからだけ取得する。AI は、どの道具をどの引数で呼ぶかを決め、その結果を比べて説明するだけにする。
2. **Gemini を使うが、Gemini に依存しない。** Gemini 固有の処理は Provider（AI サービスごとの接続部品）の中に閉じ込める。
3. **無料枠で運用する。** 初期は Gemini API の無料枠で運用する。この前提から、呼び出し回数を減らす工夫・利用上限の制御・データ利用条件の明示を、設計の必須要件として扱う（8章・9章）。
4. **AI がなくてもアプリは使える。** AI が使えないとき（上限到達・障害）でも、通常の画面（駅・時刻表・運行情報）と経路探索の API はそのまま使える。
5. **必要になるまで作らない。** 初期の Provider は Gemini と、テスト用の Fake だけにする。OpenAI や Claude は必要になった時点で追加する。

## 4. 全体構成

AI の処理はすべてバックエンド（Go / Lambda）に置く。ブラウザから Gemini などを直接呼ばない。アプリが持つ API キーがブラウザに渡るのを防ぐため。

```
Browser
  │  POST /api/chat
  ▼
handler.Chat ─────────────────────────────┐
  │                                       │ 利用上限のチェック（9章）
  ▼                                       │
ai.Service（エージェントの進行・道具の実行）│
  │                 │                     │
  │                 └─▶ tools ──▶ route（経路探索）／既存の service（駅・時刻表・運行情報・列車位置）
  ▼
ai.Provider（共通の形）
  ├── gemini.Provider ──▶ Gemini API
  └── fake.Provider（テスト用）
```

### ディレクトリ構成

```
backend/internal/ai/
├── ai.go          # Provider の共通の形、Request / Response、エラーの種類
├── service.go     # エージェントの進行（道具を呼ぶループ・回数と時間の上限）
├── tools.go       # 道具の定義（JSON Schema）と、route・既存の service への橋渡し

backend/internal/station/  # 駅名の特定（6.3）
frontend/src/pages/Chat.tsx など
```

## 5. エージェントの進行

### 5.1 function calling を使う

AI の呼び出し回数を最初から決めた流れ（AI で条件を抽出 → アプリで検索 → AI で説明）にはしない。代わりに function calling（AI がアプリ側の関数を「道具」として呼び出す仕組み）を使う。

AI が必要な道具を選んで呼び、アプリが実行した結果を受け取ってから、次の道具を呼ぶか、答えるかを決める。質問の種類ごとに処理の流れを作り込まずに済む。

```
user ──▶ AI ──(道具の呼び出し)──▶ アプリが実行 ──(結果)──▶ AI ──▶ 回答
          ▲                                                  │
          └──────────── 最大 5 往復まで ─────────────────────┘
```

- 道具を呼ぶ往復は最大 5 回とする。経路の推薦は「駅の特定 → 運行状況 → 経路 → 探し直し → 比較」で 4〜5 回かかるため。超えた場合は、その時点の情報で答えさせる。
- 1 回の往復で、互いに関係のない道具は並べて呼んでよい（例: 出発駅と到着駅の `find_station`、`get_train_status`）。往復の回数を減らすため。
- 道具はすべて読み取り専用にする。ユーザーの入力に不正な指示が混ざっていても（プロンプトインジェクション）、データの変更や外部への送信は起きない。

### 5.2 経路の推薦の流れ（system prompt で指示する）

1. 出発地と目的地の駅を `find_station` で特定する。候補が複数あるときや見つからないときは、ユーザーに聞き返して終える。
2. `get_train_status` で運行状況を確認する。
3. `search_route` で経路を探す。遅延はアプリ側で反映済み。
4. 見合わせ中の路線は、アプリが除外して探す。大きく遅れている路線（10分以上）が関わる場合は、`search_route` の中でアプリがその路線を使う経路と避けた経路の両方を探し、到着時刻の差と早い方を `comparison` として返す。
   - 当初は AI に `avoidRailways` で探し直させる設計だったが、評価セットで、Flash-Lite が比べずに遅れている路線を避けた経路だけを探し、遠回り（浅草線が20分遅れのとき、三田 → 大門 で約50分の経路）を推薦した。そのため、比較をアプリ側に移した（時刻の計算はアプリで行う、という方針にも合う。AI の往復も1回減る）。
   - 画面に出す経路（`ChatResponse.journeys`）も、到着の早い方にする。
5. 候補（到着時刻・乗り換え回数・遅れている路線を使うか）を比べ、1つを推薦する。理由と、次点の候補も短く添える。`comparison` があれば、その早い方を推薦する。

### 5.3 道具（tools）

| 道具 | 引数 | 返す内容 | Phase |
|---|---|---|---|
| `find_station` | `name` | 候補の駅（ID・駅名・路線名）。複数の場合もある | 3 |
| `get_train_status` | （なし） | 路線ごとの状態（平常 / 遅延（◯分）/ 見合わせ）。アプリが分類したもの（route-search.md 7章） | 3 |
| `search_route` | `from`, `to`, `departAt?`, `arriveBy?`, `maxTransfers?`, `avoidRailways?` | 経路の候補（乗り換え回数ごと）。遅延を反映した時刻と、反映したかどうか | 3 |
| `get_next_departures` | `stationId`, `direction?`, `after?`, `limit?` | 直近の発車（時刻・行先・種別・列車ID） | 3 |
| `get_timetable` | `stationId`, `direction?`, `calendar?`, `from?`, `to?` | 指定した時間帯の時刻表 | 3 |
| `get_train_location` | `trainId` | 列車の現在位置・遅延 | 3 |

- 道具の結果は、必要な項目と件数（例: 最大 10 件）に絞ってから AI に渡す。AI に渡すトークンを減らすため。
- 時刻の計算（「何分後」「◯時までに着くか」「どちらが何分早いか」）はアプリ側で行い、計算済みの値を返す。
- 現在時刻（JST）と運行日は、システムの指示（system prompt）で毎回 AI に渡す。運行日は `internal/calendar` の判定に従い、午前3時で切り替える。

### 5.4 駅名の特定はアプリ側で行う

AI が出力した駅名を、アプリ側で駅 ID に変換する。AI に駅 ID を推測させない。

- 同じ名前の駅が 8 つある（新宿・大門・春日・三田・神保町・蔵前・森下・熊野前）。経路探索では乗り換え駅として同じ駅に扱えるので、出発地・目的地としてはどれか1つの ID を渡せばよい。照会（次の発車など）で路線を区別する必要があるときは、候補をそのまま AI に返して、ユーザーに聞き返させる。
- 表記の揺れに対応する（「駅」の有無、空白、全角・半角）。
- ひらがなの読みでの検索は、読みの辞書を用意してから対応する（駅データには日本語名と英語名しかない）。

### 5.5 経過の表示

- レスポンスには、回答の本文に加えて、AI が呼んだ道具の一覧（道具の名前と、画面向けの短い説明。例: 「三田線の運行状況を確認」）を含める。
- 画面では、回答の上にこの一覧を表示する。エージェントが何を確かめてから推薦したかが分かるようにするため。
- 推薦した経路は、文章だけでなく、`search_route` の結果をそのまま使った経路の表示（区間・時刻・種別）も添える。時刻などの事実は、AI の文章ではなくアプリのデータで表示するため。

### 5.6 会話の状態

- サーバーは会話の状態を持たない（Lambda に状態を残さないため）。会話の履歴はブラウザが持ち、リクエストのたびに送る。
- 履歴は直近の N 往復（初期値 6）に切り詰める。トークンを節約するため。
- 道具の結果は履歴に含めない。次の質問で必要になれば、AI が道具を呼び直す。

## 6. Provider の共通の形

### 6.1 インターフェース

`generateText` だけでは function calling を表せない。そのため、会話の履歴・道具・道具の呼び出しを含む共通の形にする。

```go
type Provider interface {
    Name() string
    Generate(ctx context.Context, req Request) (Response, error)
}

type Request struct {
    Model    string
    System   string
    Messages []Message // Role: user / assistant / tool
    Tools    []Tool    // Name, Description, Parameters（JSON Schema）
}

type Response struct {
    Text      string
    ToolCalls []ToolCall // ID, Name, Arguments（JSON）
    Usage     Usage      // InputTokens, OutputTokens
}
```

- Provider ごとに異なる点（エンドポイント、認証、リクエストとレスポンスの形式、エラーの形式、道具の呼び出し方）は、それぞれの Provider の中で共通の形に変換する。
- Gemini は SDK（`google.golang.org/genai`）を使わず、REST の generateContent を `net/http` で直接呼ぶ。依存とバイナリを小さく保ち、Lambda のコールドスタートを悪化させないため。Gemini の形式は `gemini/` パッケージの外に出さない。
- Gemini 3 は、道具の呼び出しに付けた署名（`thoughtSignature`）を、同じ往復の中でそのまま送り返す必要がある。そのため、Provider が返した応答そのものを `Response.ProviderContent` として返し、エージェントは履歴の `Message.ProviderContent` に入れて送り返す。

### 6.2 エラーの種類

Provider は、元の API のエラーを次の共通の種類に変換して返す。handler は、それを HTTP ステータスとユーザー向けの文言に変換する。

| 共通のエラー | 主な原因 | HTTP | ユーザーへの表示 |
|---|---|---|---|
| `ErrAuth` | API キーが不正・無効 | 502（BYOK のときは 401） | AI サービスに接続できませんでした。設定を確認してください。 |
| `ErrRateLimited` | Provider 側の上限に到達 | 429 | 現在 AI が混み合っています。しばらくしてからお試しください。 |
| `ErrQuotaExceeded` | アプリの利用上限に到達（9章） | 429 | 本日の AI 利用上限に達しました。通常の検索をご利用ください。 |
| `ErrUnavailable` | Provider の障害 | 503 | AI サービスが一時的に利用できません。 |
| `ErrTimeout` | 応答が遅い | 504 | 応答に時間がかかっています。もう一度お試しください。 |
| `ErrInvalidModel` | 存在しないモデル | 500 | （設定の誤り。ログに記録して調査する） |
| `ErrInvalidResponse` | 応答の形式が不正 | 502 | AI の応答を処理できませんでした。 |

API 固有のエラーメッセージは、ユーザーに表示しない。ログには、エラーの種類とステータスだけを残す。

### 6.3 モデルの管理

- モデル名はコードに直接書かない。環境変数 `AI_MODEL` か、`models.go` の一覧から選ぶ。
- 一覧は `{ id, name, provider, freeTier bool }` の形で持つ。
- 初期値は、無料枠が多く、function calling を複数回続けても精度が落ちないモデルにする。軽量モデル（Flash-Lite 系など）で 11.2 の評価セットを試し、手順の判断（探し直しなど）が安定しなければ、1段上のモデルにする。実際のモデル名は、導入する時点の公式ドキュメントで確認して決める。
- 2026-10 時点の初期値は `gemini-3.5-flash-lite`。Google が新規に推奨している Flash-Lite で、無料枠がある。1段上は `gemini-3.8-flash`（[Models](https://ai.google.dev/gemini-api/docs/models)）。

## 7. 実行時間の上限

| 上限 | 値（初期値） |
|---|---|
| AI の1回の呼び出し | 10 秒 |
| 道具を呼ぶ往復 | 5 回 |
| 1回のリクエスト全体 | 25 秒（API Gateway と Lambda の 30 秒に収めるため） |

- 残り時間が少なくなったら（例: 残り 8 秒を切ったら）、それ以上道具を呼ばせず、その時点の情報で答えさせる。
- AI の呼び出しが時間切れ・一時的な障害（`ErrTimeout`・`ErrUnavailable`）で失敗したら、残り時間が 5 秒以上あれば1回だけ呼び直す。Gemini はふだん1秒前後で答えるが、評価セットの21問中3問で、最初の呼び出しが10秒を超えても返らなかったため。呼び直しも AI の呼び出しとして利用上限で数える。429（`ErrRateLimited`）は呼び直さない。
- 応答はまとめて返す（API Gateway の HTTP API はストリーミングに対応していない）。待ち時間が問題になったら、Lambda Function URL のストリーミングで経過を順に返す方式を検討する。

## 8. Gemini 無料枠での運用

### 8.1 無料枠の性質（設計に影響する点）

- 上限は API キー単位ではなく、Google Cloud のプロジェクト単位で数えられる。つまり、公開デモでは全ユーザーが1つの無料枠を共有する。
- 1日あたりの上限は、米国太平洋時間の午前0時にリセットされる。日本時間では、夏は 16 時、冬は 17 時にあたる。
- 上限の値（1分あたり・1日あたりの回数）は、モデルや時期で変わる。過去に大幅に引き下げられたこともある。値はコードに直接書かず、設定で持つ。導入する時点で公式の Rate limits のページを確認する。
- 2026-10 時点で、無料枠の具体的な値は公式ドキュメントに載っておらず、AI Studio のレート制限の画面で確認する。
- エージェントは1回の質問で AI を複数回呼ぶ（経路の推薦で最大 6 回: 道具の往復 5 回＋最後の回答）。1日に答えられる質問の数は、1日の上限の数分の一になる。

### 8.2 呼び出しを減らす工夫

| 工夫 | 内容 |
|---|---|
| AI を呼ばない近道 | 「◯◯駅 次」「遅延」「運行情報」など、決まった形の入力は AI を通さずにルールで処理する |
| 道具を並べて呼ぶ | 互いに関係のない道具は 1 回の往復でまとめて呼ばせる（5.1） |
| 往復の上限 | 道具を呼ぶ往復は最大 5 回 |
| 入力を短くする | 道具の結果を絞る、会話の履歴を切り詰める、system prompt を簡潔にする |
| キャッシュ | 運行状況のように、全員に同じ答えになる道具の結果は、短時間（30 秒程度）キャッシュする |

### 8.3 データの扱い

Gemini API の規約では、無料枠に送った内容と応答は、Google の製品改善に使われる。人が内容を確認することもある。そのため、次を必須とする。

- チャットの入力欄の近くに、次の注意書きを常に表示する。
  > 入力内容は AI の提供元（Google）に送信され、サービス改善に利用されることがあります。個人情報は入力しないでください。
- ライセンスのページに、同じ内容と Gemini API の利用規約へのリンクを載せる。
- サーバーのログに、ユーザーの入力や AI の応答の本文を残さない。残すのは、文字数・トークン数・使った道具の名前・往復の回数・エラーの種類だけにする。

将来、有料枠に切り替えた場合は、送った内容が製品改善に使われなくなる。そのときは注意書きの文言を変える。

## 9. 利用上限と乱用対策

共有の無料枠を1人で使い切られないように、アプリ側でも上限を設ける。上限は「質問の回数」ではなく「AI を呼んだ回数」で数える（1回の質問で複数回呼ぶため）。

| 制限 | 初期値（案） | 管理する場所 |
|---|---|---|
| IP ごと | 1分 5 質問 / 1日 30 質問 | DynamoDB（オンデマンド課金、TTL で自動削除）。IP はハッシュにして保存する |
| アプリ全体 | 1日の AI 呼び出し回数の上限 = Gemini 無料枠の 80% | DynamoDB |
| 1回のリクエスト | 入力 500 文字まで、履歴 6 往復まで | handler で検証 |
| API 全体 | API Gateway のスロットリング | Terraform |

- 1日の区切りは、Gemini の上限がリセットされる時刻（米国太平洋時間の午前0時）に合わせる。
- 1日の上限に達したら `ErrQuotaExceeded` を返す。IP ごとの1分の上限は、少し待てば使えるので `ErrRateLimited`（「混み合っています。しばらくしてから」）を返す。どちらも、画面には通常の検索（経路検索・駅・時刻表・運行情報）への導線を表示する。
- Phase 4 で BYOK を入れたら、上限に達したときに「自分の API キーを設定すると引き続き使えます」と案内する。

## 10. API キーの管理

### 10.1 アプリが持つキー

- AWS SSM Parameter Store の SecureString に保存する（標準パラメータは無料）。
- Lambda の IAM ロールに、そのパラメータだけを読める権限（`ssm:GetParameter`）を与える。
- `/api/chat` が初めて呼ばれたときに1回だけ読み込み、メモリに置いておく（`internal/ai/awssetup`）。AI 以外の API のコールドスタートを遅くしないため。
- キーがまだ登録されていなければ 503 を返し、1分ごとに読み直す。登録すれば再デプロイせずに使える。Gemini がキーを拒否したら（`ErrAuth`）、次の質問で読み直す（キーを差し替えたとき）。
- パラメータ名は `/<project>/<env>/gemini-api-key`。Terraform では作らず、手で登録する（値を tfstate に残さないため）。
- Lambda の実行ロールに付ける権限（このパラメータの `ssm:GetParameter`、利用上限のテーブルの `dynamodb:UpdateItem`）は `infra/bootstrap` で作る。CD の deploy 用ロールには、そのポリシーを付け外しすることだけを許す。
- キーは、ソースコード、Git、CLAUDE.md、tfvars、Lambda の環境変数のどれにも書かない。

### 10.2 BYOK（Phase 4）

このアプリにはログインもデータベースもない。そのため、サーバーにキーを保存する方式は採らない。

```
Browser（sessionStorage にキーを保存）
  │  POST /api/chat
  │  X-AI-Provider: gemini
  │  X-AI-API-Key: ****
  ▼
handler ── ai.Service ── 指定された Provider（このリクエストの間だけキーを使う）
```

| 項目 | 方針 |
|---|---|
| 保存場所 | ブラウザの sessionStorage（初期値）。ユーザーが明示的に選んだ場合だけ localStorage |
| 暗号化 | 通信経路は HTTPS。ブラウザに保存する分は暗号化しない（ブラウザ内で暗号化しても、キーを守る効果はないため）。その旨を画面に表示する |
| サーバー | 保存しない。リクエストの処理中だけメモリに置く |
| ログ | `X-AI-API-Key` ヘッダーの値を伏せ字にする処理をミドルウェアに入れる。エラーメッセージにもキーを含めない |
| 削除 | 設定画面の「削除」ボタンで、ブラウザの保存領域から消す |
| 利用上限 | BYOK のリクエストは、アプリの1日の上限（9章）の対象外にする。IP ごとの上限は適用する |

ユーザーが自分の Gemini 無料キーを持ち込めば、そのユーザーの分は別の無料枠になる。アプリの共有の無料枠を消費しないので、無料で運用するという方針とも合う。

### 10.3 設定画面（Phase 4）

```
AI 設定
  Provider  [ Gemini ▼ ]
  Model     [ （models.go の一覧から） ▼ ]
  API Key   [ ************** ]  （未設定ならアプリの共有の無料枠を使う）
  [保存] [削除]
```

```ts
type AISettings = {
  provider: "gemini"; // Provider を追加したら選択肢を増やす
  model: string;
  apiKey?: string;    // sessionStorage にだけ保存する
};
```

## 11. テスト

### 11.1 自動テスト（CI）

CI では Fake Provider を使う。実際の AI API は呼ばない（無料枠を消費しないため）。

| 対象 | 内容 |
|---|---|
| gemini.Provider | `httptest.Server` で Gemini の応答を再現し、次を確認する: 正常な応答、道具の呼び出し（複数を並べた呼び出しを含む）、認証エラー、429、5xx、タイムアウト、不正な JSON がそれぞれ正しい共通のエラーになる |
| ai.Service | Fake の応答の順番を決めておき、次を確認する: 道具を呼んで最終的に回答する流れ、探し直し（`avoidRailways` を付けた 2 回目の `search_route`）、往復の上限、全体の時間の上限、道具のエラーの扱い、Provider を差し替えても動くこと |
| tools | 各道具が、route・既存の service の結果を正しく変換すること。結果の件数が上限で切り詰められること |
| 駅名の特定 | 同名駅、表記の揺れ、存在しない駅 |
| 利用上限 | IP ごとの上限、アプリ全体の上限（AI の呼び出し回数で数えること）、BYOK のときに上限の対象外になること |
| handler | 共通のエラー → HTTP ステータスへの変換。ログにキーと本文が出ないこと |
| UI | 送信、表示、経過（呼んだ道具）の表示、経路の表示、エラーの表示、上限到達時の導線、注意書きの表示、（Phase 4）設定の保存・削除 |

### 11.2 評価セット（手動）

日本語の質問と、それぞれで期待する道具の呼び出しを 20〜30 件用意する（`backend/internal/ai/testdata/eval.yaml`）。プロンプトやモデルを変えたときに、手動で実行して精度を確認する。実際の API を呼ぶので、CI では実行しない（CI では評価セットの書き方だけを確かめる）。

```bash
cd backend && AI_EVAL=1 GEMINI_API_KEY=... go test ./internal/ai -run TestEval -v -timeout 30m
```

経路の推薦については、運行状況を固定した状態（平常・一部の路線が遅延・見合わせ）を用意し、探し直しの判断も確かめる。

```yaml
- input: "今春日にいる。浅草に行きたい"
  status: normal
  expect_tools: [find_station, get_train_status, search_route]
- input: "今春日にいる。浅草に行きたい"
  status: { "odpt.Railway:Toei.Mita": suspended }
  expect_tools: [find_station, get_train_status, search_route]
  expect_args: { search_route: { avoidRailways: ["odpt.Railway:Toei.Mita"] } }
- input: "春日駅の次の電車は？"
  expect_tools: [find_station, get_next_departures]
- input: "新宿から渋谷まで"
  expect: "都営の範囲外である旨の回答"
```
