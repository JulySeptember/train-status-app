# AI 鉄道アシスタント 設計書

- 状態: ドラフト（2026-10-07）
- 対象: `backend/internal/ai`、`POST /api/chat`、チャット UI

---

## 1. 目的

鉄道の情報を、自然言語で検索したり相談したりできる AI アシスタントを提供する。

想定する入力の例は次のとおり。

- 「この駅から次に出る電車は？」
- 「今遅れている路線はある？」
- 「春日駅の土休日の始発は何時？」
- 「新宿から浅草まで、18時までに着きたい。乗り換え少なめで」（Phase 2 で対応）

AI の役割は、ユーザーの意図を理解することと、結果を自然な文章で説明することに限る。駅・時刻・運行状況といった事実は、すべてアプリケーション側の正確なデータとロジックから取得する。

---

## 2. 基本方針

1. **AI に事実を決めさせない。** 駅・時刻表・運行情報・列車位置は、アプリケーションが持つデータからだけ取得する。AI は、どの関数をどの引数で呼ぶかを決め、その結果を説明するだけにする。
2. **Gemini を使うが、Gemini に依存しない。** Gemini 固有の処理は Provider（AI サービスごとの接続部品）の中に閉じ込める。
3. **無料枠で運用する。** 初期は Gemini API の無料枠で運用する。この前提から、呼び出し回数を減らす工夫・利用上限の制御・データ利用条件の明示を、設計の必須要件として扱う（7章・8章）。
4. **AI がなくてもアプリは使える。** AI が使えないとき（上限到達・障害）でも、通常の画面（駅・時刻表・運行情報）はそのまま使える。
5. **必要になるまで作らない。** 初期の Provider は Gemini と、テスト用の Fake だけにする。OpenAI や Claude は必要になった時点で追加する。

---

## 3. 段階的な導入

| Phase | 内容 | 前提 |
|---|---|---|
| **1** | 既存の機能で答えられる質問に対応する（次の発車・運行情報・列車位置・時刻表の照会） | AI 基盤、駅名の特定（5.3） |
| **2** | 経路探索（乗り換え・到着時刻の指定・乗り換え回数の希望） | 経路探索エンジン（別途設計） |
| **3** | BYOK（ユーザー自身の API キー）、Provider とモデルの選択 UI | Phase 1 |

### 対応範囲

- 対象は都営交通の路線だけとする（浅草線・三田線・新宿線・大江戸線・荒川線・日暮里・舎人ライナー）。
- 都営以外の路線をまたぐ質問には「対象外」と答える。
- 運賃は対象外とする。運賃機能は削除する方向で検討中で、データも欠けているため。
- 経路探索は Phase 2 まで提供しない。それまでは、経路を聞かれたら対応していない旨を答え、代わりに駅の時刻表へ案内する。

## 4. 全体構成

AI の処理はすべてバックエンド（Go / Lambda）に置く。ブラウザから Gemini などを直接呼ばない。アプリが持つ API キーがブラウザに渡るのを防ぐため。

```
Browser
  │  POST /api/chat
  ▼
handler.Chat ─────────────────────────────┐
  │                                       │ 利用上限のチェック（8章）
  ▼                                       │
ai.Service（会話の進行・道具の実行）       │
  │                 │                     │
  │                 └─▶ tools ──▶ 既存の service（駅・時刻表・運行情報・列車位置）
  ▼
ai.Provider（共通の形）
  ├── gemini.Provider ──▶ Gemini API
  └── fake.Provider（テスト用）
```

### ディレクトリ構成

```
backend/internal/ai/
├── ai.go          # Provider の共通の形、Request / Response、エラーの種類
├── service.go     # 会話の進行（道具を呼ぶループ・回数の上限）
├── tools.go       # 道具の定義（JSON Schema）と、既存の service への橋渡し
├── models.go      # 使えるモデルの一覧（設定から読み込む）
├── limit.go       # 利用上限の管理
├── gemini/        # Gemini Provider（SDK の型はここから外に出さない）
└── fake/          # テスト用の Provider
backend/internal/station/  # 駅名の特定（5.3）
frontend/src/pages/Chat.tsx など
```

## 5. AI とのやり取り

### 5.1 function calling を使う

AI の呼び出し回数を最初から決めた流れ（AI で条件を抽出 → アプリで検索 → AI で説明）にはしない。代わりに function calling（AI がアプリ側の関数を「道具」として呼び出す仕組み）を使う。

AI が必要な道具を選んで呼び、アプリが実行した結果を受け取ってから答える。質問の種類ごとに処理の流れを作り込まずに済む。

```
user ──▶ AI ──(道具の呼び出し)──▶ アプリが実行 ──(結果)──▶ AI ──▶ 回答
          ▲                                                  │
          └──────────── 最大 3 往復まで ─────────────────────┘
```

- 道具を呼ぶ往復は最大 3 回とする。超えた場合は、その時点の情報で答えさせる。
- 道具はすべて読み取り専用にする。ユーザーの入力に不正な指示が混ざっていても（プロンプトインジェクション）、データの変更や外部への送信は起きない。

### 5.2 道具（tools）

| 道具 | 引数 | 返す内容 | Phase |
|---|---|---|---|
| `find_station` | `name` | 候補の駅（ID・駅名・路線名）。複数の場合もある | 1 |
| `get_next_departures` | `stationId`, `direction?`, `after?`, `limit?` | 直近の発車（時刻・行先・種別・列車ID） | 1 |
| `get_timetable` | `stationId`, `direction?`, `calendar?`, `from?`, `to?` | 指定した時間帯の時刻表 | 1 |
| `get_train_status` | （なし） | 路線ごとの運行情報 | 1 |
| `get_train_location` | `trainId` | 列車の現在位置・遅延 | 1 |
| `search_route` | `from`, `to`, `departAt?`, `arriveBy?`, `maxTransfers?` | 経路の候補 | 2 |

- 道具の結果は、必要な項目と件数（例: 最大 10 件）に絞ってから AI に渡す。AI に渡すトークンを減らすため。
- 時刻の計算（「何分後」「◯時までに着くか」）はアプリ側で行い、計算済みの値を返す。
- 現在時刻（JST）と運行日は、システムの指示（system prompt）で毎回 AI に渡す。運行日は `internal/calendar` の判定に従い、午前3時で切り替える。

### 5.3 駅名の特定はアプリ側で行う

AI が出力した駅名を、アプリ側で駅 ID に変換する。AI に駅 ID を推測させない。

- 同じ名前の駅が 8 つある（新宿・大門・春日・三田・神保町・蔵前・森下・熊野前）。候補が複数あるときは、そのまま AI に返して、ユーザーに聞き返させる。
- 表記の揺れに対応する（「駅」の有無、空白、全角・半角）。
- ひらがなの読みでの検索は、読みの辞書を用意してから対応する（駅データには日本語名と英語名しかない）。

### 5.4 会話の状態

- サーバーは会話の状態を持たない（Lambda に状態を残さないため）。会話の履歴はブラウザが持ち、リクエストのたびに送る。
- 履歴は直近の N 往復（初期値 6）に切り詰める。トークンを節約するため。

## 6. Provider の共通の形

### 6.1 インターフェース

`generateText` だけでは function calling を表せない。そのため、会話の履歴・道具・道具の呼び出しを含む共通の形にする。

```go
type Provider interface {
    Name() string
    Generate(ctx context.Context, req Request) (Response, error)
}

type Request struct {
    Model    string
    System   string
    Messages []Message // Role: user / assistant / tool
    Tools    []Tool    // Name, Description, Parameters（JSON Schema）
}

type Response struct {
    Text      string
    ToolCalls []ToolCall // ID, Name, Arguments（JSON）
    Usage     Usage      // InputTokens, OutputTokens
}
```

- Provider ごとに異なる点（エンドポイント、認証、リクエストとレスポンスの形式、エラーの形式、道具の呼び出し方）は、それぞれの Provider の中で共通の形に変換する。
- SDK を使う場合も（Gemini なら `google.golang.org/genai`）、SDK の型は `gemini/` パッケージの外に出さない。

### 6.2 エラーの種類

Provider は、元の API のエラーを次の共通の種類に変換して返す。handler は、それを HTTP ステータスとユーザー向けの文言に変換する。

| 共通のエラー | 主な原因 | HTTP | ユーザーへの表示 |
|---|---|---|---|
| `ErrAuth` | API キーが不正・無効 | 502（BYOK のときは 401） | AI サービスに接続できませんでした。設定を確認してください。 |
| `ErrRateLimited` | Provider 側の上限に到達 | 429 | 現在 AI が混み合っています。しばらくしてからお試しください。 |
| `ErrQuotaExceeded` | アプリの利用上限に到達（8章） | 429 | 本日の AI 利用上限に達しました。通常の検索をご利用ください。 |
| `ErrUnavailable` | Provider の障害 | 503 | AI サービスが一時的に利用できません。 |
| `ErrTimeout` | 応答が遅い | 504 | 応答に時間がかかっています。もう一度お試しください。 |
| `ErrInvalidModel` | 存在しないモデル | 500 | （設定の誤り。ログに記録して調査する） |
| `ErrInvalidResponse` | 応答の形式が不正 | 502 | AI の応答を処理できませんでした。 |

API 固有のエラーメッセージは、ユーザーに表示しない。ログには、エラーの種類とステータスだけを残す。

### 6.3 モデルの管理

- モデル名はコードに直接書かない。環境変数 `AI_MODEL` か、`models.go` の一覧から選ぶ。
- 一覧は `{ id, name, provider, freeTier bool }` の形で持つ。
- 初期値は、無料枠が最も多い軽量モデル（Flash-Lite 系など）にする。実際のモデル名は、導入する時点の公式ドキュメントで確認して決める。

## 7. Gemini 無料枠での運用

### 7.1 無料枠の性質（設計に影響する点）

- 上限は API キー単位ではなく、Google Cloud のプロジェクト単位で数えられる。つまり、公開デモでは全ユーザーが1つの無料枠を共有する。
- 1日あたりの上限は、米国太平洋時間の午前0時にリセットされる。日本時間では、夏は 16 時、冬は 17 時にあたる。
- 上限の値（1分あたり・1日あたりの回数）は、モデルや時期で変わる。過去に大幅に引き下げられたこともある。値はコードに直接書かず、設定で持つ。導入する時点で公式の Rate limits のページを確認する。

### 7.2 呼び出しを減らす工夫

| 工夫 | 内容 |
|---|---|
| AI を呼ばない近道 | 「◯◯駅 次」「遅延」「運行情報」など、決まった形の入力は AI を通さずにルールで処理する |
| 往復の上限 | 道具を呼ぶ往復は最大 3 回 |
| 入力を短くする | 道具の結果を絞る、会話の履歴を切り詰める、system prompt を簡潔にする |
| キャッシュ | 運行情報のように、全員に同じ答えになる質問の結果は、短時間（30 秒程度）キャッシュする |

### 7.3 データの扱い

Gemini API の規約では、無料枠に送った内容と応答は、Google の製品改善に使われる。人が内容を確認することもある。そのため、次を必須とする。

- チャットの入力欄の近くに、次の注意書きを常に表示する。
  > 入力内容は AI の提供元（Google）に送信され、サービス改善に利用されることがあります。個人情報は入力しないでください。
- ライセンスのページに、同じ内容と Gemini API の利用規約へのリンクを載せる。
- サーバーのログに、ユーザーの入力や AI の応答の本文を残さない。残すのは、文字数・トークン数・使った道具の名前・エラーの種類だけにする。

将来、有料枠に切り替えた場合は、送った内容が製品改善に使われなくなる。そのときは注意書きの文言を変える。

## 8. 利用上限と乱用対策

共有の無料枠を1人で使い切られないように、アプリ側でも上限を設ける。

| 制限 | 初期値（案） | 管理する場所 |
|---|---|---|
| IP ごと | 1分 5 回 / 1日 30 回 | DynamoDB（オンデマンド課金、TTL で自動削除） |
| アプリ全体 | 1日の上限 = Gemini 無料枠の 80% | DynamoDB |
| 1回のリクエスト | 入力 500 文字まで、履歴 6 往復まで | handler で検証 |
| API 全体 | API Gateway のスロットリング | Terraform |

- 1日の区切りは、Gemini の上限がリセットされる時刻（米国太平洋時間の午前0時）に合わせる。
- 上限に達したら `ErrQuotaExceeded` を返す。画面には通常の検索（駅・時刻表・運行情報）への導線を表示する。
- Phase 3 で BYOK を入れたら、上限に達したときに「自分の API キーを設定すると引き続き使えます」と案内する。

## 9. API キーの管理

### 9.1 アプリが持つキー

- AWS SSM Parameter Store の SecureString に保存する（標準パラメータは無料）。
- Lambda の IAM ロールに、そのパラメータだけを読める権限（`ssm:GetParameter`）を与える。
- Lambda の起動時に1回だけ読み込み、メモリに置いておく。
- キーは、ソースコード、Git、CLAUDE.md、tfvars、Lambda の環境変数のどれにも書かない。

### 9.2 BYOK（Phase 3）

このアプリにはログインもデータベースもない。そのため、サーバーにキーを保存する方式は採らない。

```
Browser（sessionStorage にキーを保存）
  │  POST /api/chat
  │  X-AI-Provider: gemini
  │  X-AI-API-Key: ****
  ▼
handler ── ai.Service ── 指定された Provider（このリクエストの間だけキーを使う）
```

| 項目 | 方針 |
|---|---|
| 保存場所 | ブラウザの sessionStorage（初期値）。ユーザーが明示的に選んだ場合だけ localStorage |
| 暗号化 | 通信経路は HTTPS。ブラウザに保存する分は暗号化しない（ブラウザ内で暗号化しても、キーを守る効果はないため）。その旨を画面に表示する |
| サーバー | 保存しない。リクエストの処理中だけメモリに置く |
| ログ | `X-AI-API-Key` ヘッダーの値を伏せ字にする処理をミドルウェアに入れる。エラーメッセージにもキーを含めない |
| 削除 | 設定画面の「削除」ボタンで、ブラウザの保存領域から消す |
| 利用上限 | BYOK のリクエストは、アプリの1日の上限（8章）の対象外にする。IP ごとの上限は適用する |

ユーザーが自分の Gemini 無料キーを持ち込めば、そのユーザーの分は別の無料枠になる。アプリの共有の無料枠を消費しないので、無料で運用するという方針とも合う。

### 9.3 設定画面（Phase 3）

```
AI 設定
  Provider  [ Gemini ▼ ]
  Model     [ （models.go の一覧から） ▼ ]
  API Key   [ ************** ]  （未設定ならアプリの共有の無料枠を使う）
  [保存] [削除]
```

```ts
type AISettings = {
  provider: "gemini"; // Provider を追加したら選択肢を増やす
  model: string;
  apiKey?: string;    // sessionStorage にだけ保存する
};
```

## 10. 実行環境の制約

| 制約 | 対応 |
|---|---|
| API Gateway と Lambda のタイムアウト（30 秒） | AI の1回の呼び出しは 10 秒でタイムアウトにする。往復は最大 3 回。全体で 25 秒を超えそうなら途中で打ち切る |
| ストリーミングで返せない（API Gateway の HTTP API は対応していない） | 初期は応答をまとめて返す。必要になったら Lambda Function URL のストリーミングを検討する |
| コールドスタート | AI の SDK を追加すると起動が遅くなる。Issue #9（時刻表データの軽量化）を先に完了させる |
| メモリ 256MB | Gemini の SDK を足したあとに、Max Memory Used を計測する |

## 11. テスト

### 11.1 自動テスト（CI）

CI では Fake Provider を使う。実際の AI API は呼ばない（無料枠を消費しないため）。

| 対象 | 内容 |
|---|---|
| gemini.Provider | `httptest.Server` で Gemini の応答を再現し、次を確認する: 正常な応答、道具の呼び出し、認証エラー、429、5xx、タイムアウト、不正な JSON がそれぞれ正しい共通のエラーになる |
| ai.Service | Fake の応答の順番を決めておき、次を確認する: 道具を呼んで最終的に回答する流れ、往復の上限、道具のエラーの扱い、Provider を差し替えても動くこと |
| tools | 各道具が、既存の service の結果を正しく変換すること。結果の件数が上限で切り詰められること |
| 駅名の特定 | 同名駅、表記の揺れ、存在しない駅 |
| 利用上限 | IP ごとの上限、アプリ全体の上限、BYOK のときに上限の対象外になること |
| handler | 共通のエラー → HTTP ステータスへの変換。ログにキーと本文が出ないこと |
| UI | 送信、表示、エラーの表示、上限到達時の導線、注意書きの表示、（Phase 3）設定の保存・削除 |

### 11.2 評価セット（手動）

日本語の質問と、それぞれで期待する道具の呼び出しを 20〜30 件用意する（`backend/internal/ai/testdata/eval.yaml`）。プロンプトやモデルを変えたときに、手動で実行して精度を確認する。実際の API を呼ぶので、CI では実行しない。

```yaml
- input: "春日駅の次の電車は？"
  expect_tools: [find_station, get_next_departures]
- input: "新宿駅の大江戸線の時刻表"
  expect_tools: [find_station, get_timetable]
- input: "新宿から渋谷まで"
  expect: "都営の範囲外である旨の回答"
```
